# Архитектура бэкенда учебного тренажёра оператора ДДС (АРМ-112)

Документ описывает функциональную и компонентную архитектуру (ТЗ, раздел «Требования к
решению»). Установка и эксплуатация: `README.md`. Контракт API: `../api.txt` и
`GET /api/v1/openapi.json`.

## 1. Назначение и границы

Тренажёр имитирует рабочее место оператора системы-112: обучающийся принимает учебный
звонок (голосом или текстом), заполняет карточку происшествия, система сравнивает его
действия с эталоном сценария и оценивает по полям, порядку действий, времени и оформлению
текста. Преподаватель настраивает сценарии (в том числе с помощью локальной нейросети),
проводит занятия и аттестации, получает отчёты и аналитику. Администратор отвечает за
техническое состояние комплекса.

Границы (ТЗ): реальные вызовы не обрабатываются, боевая система-112 не подключается,
внешние сети не используются. Все компоненты работают в локальном контуре.

## 2. Компонентная архитектура

```
                 https (443)
браузер ──────────────► proxy (nginx, TLS) ──► /api/*  ──► arm_api (Flask + gunicorn, N узлов) ──► PostgreSQL
   │                          │                               │   │
   │  wss://хост/ws           └─► /ws ──► asterisk            │   └─► llm (llama.cpp, YandexGPT-5-Lite-8B)
   └─ софтфон (SIP по WebRTC)             ▲   │               │
                                          │   └─ record/play  │
                                          └── ARI ── arm_voip ◄┴──► voice (Piper TTS + faster-whisper STT)
                                                        │  (события: /internal/voip/events,
                                                        │   реплики диалога: /internal/calls/{id}/voice-turn)
```

| Компонент | Технологии | Ответственность |
|---|---|---|
| `proxy` | nginx | TLS 1.2/1.3, wss, gzip, раздача собранного фронтенда, проксирование `/api` и `/ws` |
| `arm_api` | Python, Flask, gunicorn, SQLAlchemy, Alembic | вся бизнес-логика, REST API JSON и XML, RBAC, аудит, оценка, отчёты, бэкапы |
| `postgres` | PostgreSQL 16 | единственное хранилище состояния (совместимость с MySQL/MariaDB и SQLite для стендов) |
| `asterisk` | Asterisk (PJSIP, ARI, WebRTC) | SIP-сервер локального контура, медиа, запись звонка |
| `arm_voip` | Python, FastAPI, websockets | пул SIP-номеров, управление звонками по ARI, воспроизведение звука сценария и ответов ИИ, запись реплик оператора, замер задержки (RTT), события в `arm_api` |
| `voice` | Piper (TTS, ONNX), faster-whisper (STT, CTranslate2), FastAPI | офлайн синтез речи заявителя и распознавание речи оператора; отдельный образ (`python:3.12`), т.к. этой ML-экосистеме нужна более старая версия Python, чем у `arm_api`/`arm_voip` (`python:3.14`) |
| `llm` | llama.cpp, YandexGPT-5-Lite-8B-instruct (GGUF, Q4_K_M) | генерация и коррекция сценариев, смысловая проверка, формулировки инсайтов, живые реплики заявителя в диалоге |
| служба буфера | `python -m arm_api.services.spool run` | повторная обработка ответов, принятых при недоступной БД |
| планировщик | поток `backup.run_loop` | ежедневная копия и очистка журнала, лидер выбирается через БД |

### Голосовой диалог (речь оператора -> текст -> ИИ -> речь -> VoIP)

По умолчанию выключен (`VOICE_DIALOG_ENABLED=0` в `arm_voip`). При включении звонок перестает
быть «имитацией с готовой фонограммой» и становится живым диалогом с ИИ-заявителем:

1. `arm_voip` записывает реплику оператора через ARI (`record`, останов по паузе или таймауту)
   и пересылает WAV сервису `voice` (`POST /stt`) - результат - обычный текст.
2. Текст уходит в `arm_api` (`POST /internal/calls/{id}/voice-turn`), где `services.ai.caller_turn`
   генерирует ответ заявителя с учетом легенды сценария и истории разговора (та же функция, что и
   у текстового чата `POST /attempts/{id}/messages` - реплики хранятся в одной стенограмме).
3. Ответ уходит обратно в `arm_voip`, озвучивается через `voice` (`POST /tts`, Piper) и
   проигрывается в канал оператора (ARI `play`), после чего цикл повторяется.

Каждый шаг деградирует по отдельности: недоступен `voice` - реплика пропускается, а не рвёт
звонок; ИИ выключен или не ответил - используются заготовки сценария (`legend.followups`),
как было до этой функции.

`arm_api` не хранит состояния между запросами: токены самодостаточны, ответы и черновики
лежат в БД. Поэтому любой узел обслужит любой запрос (см. раздел 7).

### Структура кода `arm_api/src/arm_api`

| Слой | Каталог | Содержание |
|---|---|---|
| Ядро | `core/` | конфигурация из окружения, RBAC и токены (`security.py`), ошибки, пагинация, XML-слой (`xmlapi.py`), JSON-логи |
| Модели | `models/` | 27 моделей и связующие таблицы (раздел 4) |
| Маршруты | `routes/` | тонкий слой: разбор запроса, проверка прав, вызов сервиса, ответ |
| Сервисы | `services/` | оценка, грамматика, аналитика, отчёты, ИИ, база знаний, бэкапы, оповещения, аттестация, обновления, буфер, кластер |

## 3. Функциональная архитектура

### 3.1 По ролям

**Администратор** (`routes/system.py`, `users.py`, `workstations.py`, `updates.py`):
пользователи и блокировки; матрица прав ролей (`/roles/matrix`, с обязательными и
запрещёнными правами); состояние компонентов (`/system/health`, `metrics`, `events`);
оповещения и их доставка (webhook, почта); настройки VoIP, бэкапа, журналирования,
производительности, безопасности (`/system/settings`, XML-обмен); резервные копии и
восстановление; журнал аудита с проверкой целостности; отчёты об ошибках и сбоях;
пакетное обновление контента; рабочие места АРМ и их XML-конфигурации. Администратор не
меняет оценки и сценарии, не видит результатов обучающихся, не удаляет данные без свежей
копии.

**Преподаватель** (`routes/scenarios.py`, `sessions.py`, `results.py`, `reports.py`,
`materials.py`): сценарии (создание, импорт JSON, генерация ИИ, предпросмотр эталона,
частичное и полное утверждение, коррекция комментарием, проверка грамматики); занятия
(категории, сложность, лимит времени, источник карточек: сгенерированные, обучающихся,
смешанный; профиль оценивания; режим аттестации); мониторинг в реальном времени;
экспертная оценка с записью в аудит; отчёты json, csv, xlsx, pdf с возможностью
обезличивания; сертификаты; инсайты по типичным ошибкам группы; методические материалы.

**Обучающийся** (`routes/sessions.py`, `results.py`, `materials.py`): назначенные занятия,
получение карточки и звонка, ответ на вызов, диалог с заявителем, черновик, отправка,
собственные результаты, прогресс, прогноз, разбор ошибок, справочная база.

### 3.2 Основной поток занятия

```
преподаватель: POST /sessions → /start
обучающийся:   POST /sessions/{id}/attempts/next   выбор сценария, лимит времени, прогноз балла
               POST /attempts/{id}/answer          принять вызов: с этого момента идет норматив
               PUT  /attempts/{id}/draft           черновик (сохранность при сбое)
               POST /attempts/{id}/submit          оценка, замечания, зачет
преподаватель: POST /sessions/{id}/finish          закрытие открытых карточек, итог аттестации
               POST /reports                       отчет о занятии
```

**Выбор лимита времени** (`resolve_time_limit`): занятие, затем сценарий, затем профиль
оценивания, затем 30 с (ТЗ).

### 3.3 Оценка (`services/scoring.py`)

Балл складывается из частей с весами профиля оценивания: поля карточки (нечёткое
сравнение текста, отдельная сверка чисел и телефонов), порядок и полнота действий,
время относительно норматива с допуском, оформление и орфография
(`services/grammar.py`, pymorphy3). Необязательная смысловая проверка нейросетью
(`AI_SCORING_ENABLED`) подключается как «судья» для текстовых полей. Вердикт содержит
разбор по полям, что и используется в отчётах и разборе ошибок ИИ.

### 3.4 Режим аттестации (`services/attestation.py`)

Флаг в `training_sessions.settings`: фиксированный проходной балл и минимум карточек;
пока занятие идёт, обучающийся видит только балл и зачёт; при завершении считается итог,
успешно прошедшим выдаётся сертификат, протокол входит в отчёт.

### 3.5 ИИ-модуль (`services/ai.py`, `services/knowledge.py`)

Работает только с локальным сервером `llm`. Функции: генерация сценариев по категориям,
сложности, месту и подсказкам; коррекция сценария по комментарию преподавателя;
формулировки инсайтов; смысловая проверка ответа. Загруженные материалы разбираются на
фрагменты (pdf, docx, txt, csv, json, xml), а самые подходящие по запросу (основы слов
с весами IDF) подставляются в запрос к модели: так «Памятка для ДДС» влияет на сценарии
без дообучения. Всё, что создала модель, попадает на утверждение преподавателя.
Отказ модели не ломает остальную систему (ответ 503 только у ИИ-функций, правила
аналитики работают без модели).

### 3.6 Аналитика и прогноз (`services/analytics.py`)

Статистика по обучающемуся, группе, занятию; тепловая карта ошибок; линейный прогноз
следующего балла по последним оценкам (с `r2`). Прогноз сохраняется в карточке при
выдаче и сравнивается с фактом: `GET /analytics/forecast-accuracy` (MAE, RMSE, смещение,
доля попаданий, выигрыш у наивного прогноза, уровень достоверности).

Модели (27) и связующие таблицы, PostgreSQL 16, схема Alembic:

## 5. Безопасность

- Аутентификация: пароль (не менее 10 знаков, цифра и буква), TOTP как второй фактор,
  блокировка после серии неудач, короткоживущие access-токены и refresh с ротацией.
- Авторизация: RBAC по 18 правам; проверки владельца (преподаватель видит свои занятия,
  обучающийся только свои результаты); матрица прав редактируется через API в рамках
  правил ТЗ; права проверяются по БД при каждом запросе, изменения действуют сразу
  (исключение: при недоступной БД ответы обучающегося принимаются в буфер по правам из
  подписанного токена, полную проверку делает повторная обработка).
- Каналы: TLS на nginx, wss для софтфона; секретные настройки скрыты в ответах и не
  попадают в журналы (адрес webhook, токены).
- Аудит: все значимые действия с хэш-цепочкой, хранение не менее 183 дней.
- Персональные данные (152-ФЗ): согласие, обезличивание записей и отчётов.
- Загружаемое: проверка типа и расширения, XML разбирается защищённым парсером (XXE,
  «миллиард смеющихся»), архивы обновлений проверяются на выход из каталога, ссылки и
  размер (защита от zip-бомбы).

## 6. Надёжность

| Угроза | Механизм |
|---|---|
| Сбой БД во время занятия | буфер на диске (`services/spool.py`): ответ обучающегося принимается с ответом 202 и обрабатывается после восстановления с временем получения, повтор идемпотентен |
| Сбой сети клиента до 30 с | черновики и refresh-токены, время ведёт сервер |
| Потеря данных | ежедневный бэкап (pg_dump/mysqldump/sqlite), контрольные суммы, ротация, восстановление; разрушающие операции только после свежей копии |
| Падение сервиса | политика перезапуска контейнеров, повторная обработка буфера |
| Сбой, который надо заметить | оповещения `/system/alerts`, доставка webhook и почтой |
| Обновление данных | пакет применяется целиком или никак, только вне занятий и после копии |

## 7. Масштабирование

- **Вертикальное:** процессы и потоки gunicorn, размер пула соединений с БД задаются в
  `/system/settings` (`perf.*`) или переменных окружения и применяются при перезапуске узла.
- **Горизонтальное:** узлы `arm_api` равноправны и работают с одной БД (`services/cluster.py`);
  миграции и фоновые задания выполняет один узел, выбор через блокировки СУБД
  (advisory lock PostgreSQL, GET_LOCK MySQL). Балансировка на nginx. Ограничение: пул
  номеров и активные звонки VoIP живут в памяти одного процесса `arm_voip`.

## 8. Измеренные показатели (локальный стенд)

Стенд: Apple M-серии, 8 ядер, 8 ГБ ОЗУ, PostgreSQL 16 и генератор нагрузки на той же машине,
gunicorn 4 процесса × 8 потоков, текстовый канал. Стенд заметно слабее требований ТЗ к серверу.

| Показатель ТЗ | Норма | Результат |
|---|---|---|
| Отклик при 20 пользователях | ≤ 2 с | p95 ≤ 0,14 с, 349 запросов/с, ошибок 0 |
| Отклик при 100 пользователях, подключение за 15 с | ≤ 2 с | p95 ≤ 0,56 с, 331 запрос/с, ошибок 0 |
| То же, все 100 входят в одну секунду | ≤ 2 с | операции с карточкой p95 ≤ 0,81 с; вход p95 = 2,43 с (вход намеренно тяжёлый: PBKDF2, 600 тыс. итераций) |
| Запись в БД | ≥ 100 оп/с | 3700–5000 транзакций/с (запись = транзакция) |
| Отчёт по 20 676 карточкам | ≤ 30 с | json 11,4 с, csv 7,6 с, xlsx 7,6 с, pdf 10,8 с (PDF сокращается до 3000 строк) |
| Задержка голоса VoIP | ≤ 150 мс | не измерялась: нужен стенд с Asterisk (замер RTT по RTCP реализован) |

Воспроизведение: `arm_api/tools/loadtest.py` (описание в заголовке скрипта).

## 9. Развёртывание

`docker compose up -d --build` поднимает `arm_api`, `postgres`, `arm_voip`, `asterisk`,
`proxy`; ИИ (`llm`) и голосовой диалог (`voice`) добавляются профилем `ai`
(`docker compose --profile ai up -d`, модели - `llm/download_model.sh` и
`voice/download_models.sh`). Для кластера узлы `arm_api` запускаются с
`RUN_INIT=0` и `RUN_SCHEDULER=0` (кроме одного). Обновление кода и образов выполняется
пересборкой; учебный контент и настройки обновляются пакетами через `POST /system/updates`.

## 10. Ограничения

- Docker на стенде разработки не запускался: Asterisk, `llm`, nginx и образы проверены
  на уровне конфигурации и тестов с подменой; требуется прогон на стенде с docker.
- Качество сценариев ИИ зависит от модели и подсказок; на слабом сервере генерация медленная.
- Расшифровка звука (MP3/WAV) для базы знаний не выполняется.
- Голосовой диалог (`VOICE_DIALOG_ENABLED`) проверен модульными тестами (запись, распознавание,
  генерация ответа, синтез, повторные попытки, лимит реплик - все со стороны кода и с локально
  проверенным реальным циклом TTS→STT), но не живым звонком через Asterisk: нужен стенд с docker.
  Диалог по одному каналу идет по очереди (сказал оператор - ответил заявитель), без наложения
  речи - это ограничение модели «один канал ARI на звонок», а не текущей реализации.
- Интерфейс и софтфон (JsSIP) не входят в бэкенд.
