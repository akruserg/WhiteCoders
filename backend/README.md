# Бэкенд учебного тренажёра оператора ДДС (АРМ-112)

REST API, VoIP-эмуляция звонков и локальный ИИ-модуль. Работает в изолированном
контуре, во внешние сети не обращается.

Документы: [ARCHITECTURE.md](ARCHITECTURE.md) (функциональная и компонентная архитектура),
[API_CHANGES.md](API_CHANGES.md) (что изменилось в API для фронтенда), `../api.txt` (маршруты).

## Состав

```
                 https (443)
браузер ──────────────► proxy (nginx, TLS) ──► /api/*  ──► arm_api (Flask + gunicorn) ──► PostgreSQL
   │                          │                                │  │
   │  wss://хост/ws           └─► /ws ──► asterisk             │  └─► llm (llama.cpp, YandexGPT-5-Lite-8B)
   └─ софтфон (SIP по WebRTC)             ▲   │                │
                                          │   └─ record/play   │
                                          └── ARI ── arm_voip ◄┴──► voice (TTS Piper + STT faster-whisper)
```

| Сервис | Папка | Назначение |
|---|---|---|
| `arm_api` | `arm_api/` | REST API: пользователи, сценарии, занятия, оценка, отчёты, аудит |
| `postgres` | | база данных (PostgreSQL 16) |
| `arm_voip` + `asterisk` | `arm_voip/` | звонки, пул SIP-номеров, звук сценария, замер задержки (см. `arm_voip/README.md`) |
| `llm` | `llm/` | ИИ: генерация сценариев, коррекция, инсайты, смысловая проверка, живые реплики заявителя |
| `voice` | `voice/` | офлайн-озвучка заявителя (TTS) и распознавание речи оператора (STT) для живого голосового диалога |
| `proxy` | `proxy/` | HTTPS/wss, раздача собранного фронтенда |

## Требования

Docker 24+ и Docker Compose v2. ОС: Ubuntu 20.04+ или Windows 10/11 с Docker Desktop.

**Сервер (по ТЗ, для работы ИИ-модуля):** процессор Intel Core i7 / Xeon или
аналог от 6 ядер, ОЗУ от 32 ГБ, накопитель NVMe SSD от 512 ГБ, сеть Gigabit Ethernet.
Без ИИ-модуля хватает 4 ядер и 8 ГБ ОЗУ.

**Рабочее место обучающегося (АРМ):** Intel Core i5 или аналог, ОЗУ от 16 ГБ, SSD от
256 ГБ, Gigabit Ethernet, гарнитура с поддержкой VoIP (или программный софтфон).
Браузеры: актуальные Chrome, Firefox, Яндекс.Браузер.

## Установка

```bash
cd backend

# 1. Настройки. Везде заменить CHANGE_ME (секреты не коммитить, .env в .gitignore)
cp arm_api/.env_example  arm_api/.env
cp arm_voip/.env_example arm_voip/.env
#    arm_api/.env:  SECRET_KEY, POSTGRES_*, CORS_ORIGINS, ARM_VOIP_SERVICE_TOKEN,
#                   VOIP_ENABLED=1, ADMIN_USERNAME / ADMIN_PASSWORD
#    arm_voip/.env: ARI_PASSWORD, VOIP_SIP_SECRET, тот же ARM_VOIP_SERVICE_TOKEN

# 2. Запуск (без ИИ)
docker compose up -d --build

# 3. Проверка
curl -k https://localhost/health            # {"status": "ok"}
```

При первом запуске контейнер сам применяет миграции и наполняет БД:
классификатор происшествий (23 группы, 1281 тип из официального файла v046.11),
шаблон карточки АРМ-112, профиль оценивания, роли и права, настройки системы.
Если заданы `ADMIN_USERNAME` и `ADMIN_PASSWORD`, создаётся администратор. Иначе:

```bash
docker compose exec arm_api python seed_admin.py --username admin --password '<пароль от 10 знаков>'
```

Для демонстрации добавьте `SEED_DEMO=1` в `arm_api/.env`: появятся три готовых
утверждённых сценария (пожар в квартире, ДТП, прорыв воды).

### ИИ-модуль (YandexGPT-5-Lite-8B-instruct)

```bash
./llm/download_model.sh                  # один раз, ~5 ГБ, нужен интернет
# arm_api/.env: AI_ENABLED=1  (и AI_SCORING_ENABLED=1 для смысловой проверки ответов)
docker compose --profile ai up -d
```

Модель работает локально через llama.cpp, на CPU генерация одного сценария занимает
около минуты. Каталог `llm/models` можно скопировать на закрытый сервер.
Что делает ИИ: генерирует черновики сценариев по категориям и сложности, применяет
комментарий преподавателя к сценарию, формирует инсайты по ошибкам группы и
рекомендации обучающемуся, при `AI_SCORING_ENABLED=1` сверяет по смыслу текстовые
поля, которые не совпали с эталоном (числа, адреса и телефоны нейросеть не сверяет).
Без модели инсайты строятся правилами, генерация сценариев отвечает 503.
Лицензия модели: `llm/models/LICENSE` (коммерческое использование бесплатно до
10 млн выходных токенов в месяц).

### Голосовой диалог (озвучка звонка, живой ответ ИИ-заявителя)

```bash
cd voice && poetry install && poetry run sh download_models.sh && cd ..   # один раз, ~600 МБ
# voice/.env:      VOICE_SERVICE_TOKEN
# arm_voip/.env:   VOICE_DIALOG_ENABLED=1, тот же VOICE_SERVICE_TOKEN
docker compose --profile ai up -d
```

Без этой настройки звонок либо идёт без звука, либо (если в сценарий вручную положена
запись) проигрывает один и тот же файл каждый раз - именно то, что раньше называлось
«эмуляцией вызова» без живого голоса. С `VOICE_DIALOG_ENABLED=1` цикл такой: оператор
говорит -> `voice` распознает речь (faster-whisper) -> `arm_api` генерирует ответ
заявителя нейросетью с учетом легенды сценария (`llm`, тот же модуль, что и для
сценариев) -> `voice` озвучивает ответ (Piper) -> звучит в трубке оператора - и так
по кругу, пока оператор не закончит или не исчерпан лимит реплик (`VOICE_DIALOG_MAX_TURNS`).
Подробности и офлайн-модели: `voice/README.md`. Если `voice` или `llm` недоступны -
звонок продолжается без этой реплики (не рвётся), как и при отключенном ИИ.

### HTTPS

Прокси создаёт самоподписанный сертификат при первом запуске (`TLS_HOST` в
окружении задаёт имя). Свой сертификат положите в том `proxy_certs` как
`server.crt` и `server.key`. Собранный фронтенд монтируется из `frontend/dist`.

## Учётные записи и роли

| Роль | Что может |
|---|---|
| Администратор | учётки, роли, блокировки, настройки, бэкапы, журналы, аудит, метрики. Не видит результаты обучающихся, не меняет оценки и сценарии, отчёты только системные |
| Преподаватель | сценарии, генерация ИИ, занятия, мониторинг, экспертная оценка (с записью в аудит), отчёты, аналитика, сертификаты |
| Обучающийся | назначенные занятия, карточки и звонки, свой прогресс и ошибки, справочная база |

Вход по паролю (не менее 10 символов, буква и цифра), необязательно TOTP. После
5 неудачных попыток учётка блокируется (порог меняется в настройках).

## Настройки

Значения по умолчанию задаёт окружение (`.env_example` подробно описывает каждое),
часть из них администратор меняет без перезапуска в `/system/settings`:
`voip.enabled`, `voip.max_latency_ms`, `backup.keep_count`, `backup.enabled`,
`audit.retention_days`, `ai.enabled`, `ai.scoring_enabled`, `security.max_failed_logins`.
Пока настройку не менял человек, она следует за `.env` (правка файла и перезапуск
действуют); после правки через API приоритет у БД.

**XML-конфигурация.** Все несекретные настройки выгружаются одним файлом
(`GET /system/settings/export.xml`) и загружаются обратно
(`POST /system/settings/import`, тело XML). Разбор защищён от XXE и вложенных
сущностей, применяется целиком или не применяется вовсе, изменение пишется в аудит.

**Сервисы.** `GET /system/services` показывает состояние, а
`POST /system/services/{voip|ai|scheduler}/{start|stop}` логически включает и
выключает сервис (VoIP-звонки, ИИ-модуль, ежедневное задание бэкапа). Сами
контейнеры запускает и останавливает docker compose.

## Персональные данные (152-ФЗ)

- Согласие: при входе профиль содержит `consent_required`; после
  `POST /auth/consent` время согласия сохраняется в `users.pd_consent_at`.
- Обезличивание: `POST /users/{id}/anonymize` (администратор) заменяет ФИО, логин
  и почту, закрывает вход, результаты занятий остаются для статистики.
- Отчёты: параметр `params.anonymize = true` заменяет ФИО на «Обучающийся N».
- Администратору доступны только системные отчёты, результаты обучающихся он не
  видит. Преподаватель строит отчёты, инсайты и тепловую карту только по своим
  занятиям и группам.
- Удаление группы и обезличивание разрешены только при наличии успешной
  резервной копии за последние 24 часа (`409 backup_required`).

## Резервное копирование и восстановление

Копия БД (pg_dump) делается раз в сутки в 03:00 UTC и по кнопке в разделе
администрирования (`POST /system/backups`). Хранятся последние 30 (настройка
`backup.keep_count`), файлы лежат в томе `arm_data`, каталог `backups`.

Восстановление (API остановить, чтобы никто не писал в БД):

```bash
docker compose stop arm_api
docker compose run --rm --no-deps arm_api \
    python -m arm_api.services.backup restore /var/lib/arm112/backups/backup_<id>.dump
docker compose up -d arm_api
```

Журнал аудита хранится не менее 6 месяцев (по умолчанию 190 дней), старше срока
записи удаляются ежедневным заданием. Целостность проверяется:
`GET /system/audit/verify`.

## Логи и мониторинг

Журнал приложения пишется в stdout в формате JSON (одна строка на запись,
`LOG_FORMAT=text` для отладки): `docker compose logs -f arm_api`. Состояние
компонентов: `GET /api/v1/system/health` (API, БД, VoIP, ИИ), нагрузка и ёмкость:
`/system/metrics`, оповещения о сбоях и задержке голоса: `/system/alerts`.

## Разработка и тесты

```bash
cd arm_api && pip install -e . pytest && pytest              # 166 тестов
cd ../arm_voip && pip install -e . pytest pytest-asyncio && pytest   # 41 тест
black --check arm_api arm_voip && flake8 arm_api arm_voip
```

Контракт API: `../api.txt` (список) и `GET /api/v1/openapi.json` (полный).
Обновить `api.txt`: `arm_api/tools/dump_api.py`.

**Нагрузочная проверка** (ТЗ: отклик до 2 с, 20 одновременных сессий):
`arm_api/tools/loadtest.py` проходит цикл «карточка, вызов, черновик, отправка» за
N пользователей и сравнивает p95 с нормой ТЗ; `--ramp N` подключает пользователей
плавно. Запуск и формат файла пользователей описаны в заголовке скрипта.

## Методы обработки данных

- **Оценка карточки** (`services/scoring.py`): сравнение с эталоном по полям
  (нечёткое совпадение текста с отдельной сверкой чисел, телефоны по цифрам),
  порядок и полнота действий, укладывание в норматив времени с допуском, ошибки
  оформления. Веса, пороги и число допустимых ошибок задаёт профиль оценивания.
- **Грамматика** (`services/grammar.py`): правила оформления записи (пробелы,
  регистр, парные скобки, смешение алфавитов, повторы) и орфография по
  морфологическому словарю pymorphy3 (все формы слов, предлагается исправление).
  Аббревиатуры, имена внутри предложения и слова из условий сценария не считаются
  ошибками; правило `spelling` отключается в `syntax_rules` профиля оценивания.
- **Карточки обучающихся**: `POST /attempts/{id}/scenario` превращает оцененную
  карточку в сценарий (`origin = student`) на утверждение преподавателю; после
  утверждения он попадает в занятия с источником `student` или `mixed`.
- **Аудит** (`core/security.py`): каждая запись включает хэш предыдущей, подмена
  или удаление записи обнаруживается проверкой цепочки.

## Ограничения

- Пул номеров и активные звонки VoIP хранятся в памяти одного процесса
  `arm_voip`; после его перезапуска текущие звонки теряются.
- Нагрузку измеряли на слабой машине (8 ядер, 8 ГБ, БД и генератор на ней же), результаты в
  `ARCHITECTURE.md`, раздел 8. На целевом сервере (6+ ядер, 32 ГБ) прогон нужно повторить
  скриптом `tools/loadtest.py`. Задержку голоса (150 мс) можно измерить только на живом Asterisk.
- Вход тяжёлый намеренно (PBKDF2, 600 тыс. итераций): если все 100 человек входят в одну
  секунду, p95 входа выходит за 2 с; при обычном подключении в течение 15 с укладывается.
- Орфография опирается на словарь общего языка: редкие профессиональные термины
  могут отмечаться как возможная ошибка (замечание мягкое, слова сценария исключены).
- Запуск с ИИ проверен на уровне интерфейса и контрактов (тесты с подменой
  сервера модели); качество сценариев зависит от модели и подсказок преподавателя,
  все сгенерированные сценарии проходят утверждение преподавателем.
